# Building and Testing

## CMake presets

The following presets are defined in `CMakePresets.json`:

| Preset | Build directory | Purpose |
|---|---|---|
| `debug` | `build/Debug` | Day-to-day development |
| `release` | `build/Release` | Optimised production build |
| `sanitize` | `build/Sanitize` | AddressSanitizer + UndefinedBehaviorSanitizer |
| `tsan` | `build/TSan` | ThreadSanitizer — catches data races |
| `coverage` | `build/Coverage` | LLVM source-based coverage instrumentation |
| `fuzz` | `build/Fuzz` | libFuzzer fuzz targets (ASan enabled) |
| `cross-arm64` | `build/CrossArm64` | Cross-compile for aarch64-linux-gnu |

All presets use the Ninja generator and inherit from a hidden `base` preset that reads
`CMAKE_C_COMPILER_LAUNCHER` and `CMAKE_CXX_COMPILER_LAUNCHER` from environment variables. In CI
these are set to `ccache`; locally they are unset and have no effect unless you configure them
yourself.

The `debug`, `sanitize`, `tsan`, `coverage`, and `fuzz` presets share the Conan toolchain
generated by `conan install --profile=conan/profiles/x86_64/debug`. The `cross-arm64` preset
exists for local cross-compilation — see [cross-compilation.md](cross-compilation.md). In CI,
ARM64 is tested natively on an `ubuntu-22.04-arm` runner using the standard `debug` preset.
Running the **Conan: Install** task creates the debug and release toolchain files.

## Building

Via VS Code tasks:

- **CMake: Build All** — configures and builds all targets for the selected preset (default build
  task, `Ctrl+Shift+B`)
- **CMake: Build Target…** — prompts for a target name, then configures and builds only that target
- **CMake: Configure** — runs configure only, without building

Via the command line:

```bash
cmake --preset debug
cmake --build --preset debug
```

```bash
cmake --preset release
cmake --build --preset release
```

## compile_commands.json and IntelliSense

`CMAKE_EXPORT_COMPILE_COMMANDS ON` is set in `CMakeLists.txt`. CMake writes
`compile_commands.json` to the preset's build directory after configure. clangd is configured to
read from `build/Debug/compile_commands.json`.

Run a Debug build after adding any new source file so clangd picks up the updated compilation
database.

## Protobuf codegen

`proto/CMakeLists.txt` calls `protobuf_generate_cpp()` on every `.proto` file in the directory.
Generated `.pb.h` and `.pb.cc` files are written to `build/<Preset>/proto/` at build time.

The `orion_proto` CMake target exposes the generated headers:

```cmake
target_include_directories(orion_proto PUBLIC ${CMAKE_CURRENT_BINARY_DIR})
```

To use generated types in another target:

```cmake
target_link_libraries(my_target PRIVATE orion_proto)
```

The include path is inherited automatically — no manual `include_directories` call is needed.

## Formatting

Both formatters auto-fix in place. Run them before committing to satisfy the pre-commit checks.

| Task | Tool | Scope |
|---|---|---|
| **Format: C++** | clang-format-18 | All `*.cpp` and `*.hpp` files outside `build/` |
| **Format: CMake** | gersemi | All `CMakeLists.txt` and `*.cmake` files |

These tasks delegate to the `format-clang` and `format-cmake` CMake targets defined in
`cmake/tools.cmake`.

## Testing

Tests use GoogleTest and are registered with CTest via `gtest_discover_tests`. CTest presets
mirror the build presets.

Run all tests:

```bash
cmake --build --preset debug
ctest --preset debug
```

Or via VS Code: **CMake: Run Tests**.

Test output is only printed on failure (`outputOnFailure: true` in `CMakePresets.json`).

## Linting

**Lint: C++** runs `run-clang-tidy` via the `tidy` CMake target. The target constrains analysis
to files under `libs/`, `proto/`, and `tests/` using a path filter, which prevents clang-tidy
from running on generated protobuf sources in `build/`.

The compile database from the active build directory is used, so run a build before linting to
ensure the database is current.

See [coding-standards.md](coding-standards.md) for the full set of enforced checks and naming
conventions.

## CI format checks

These are what the pre-commit hooks enforce. Unlike the formatting tasks, they do not modify files —
they exit non-zero if any file is out of compliance.

| Task | Equivalent command |
|---|---|
| **CI: Check Format (C++)** | `clang-format-18 --dry-run --Werror <files>` |
| **CI: Check Format (CMake)** | `gersemi --check .` |
| **CI: Check All** | Both of the above in parallel |

## Sanitizers

The `sanitize` and `tsan` presets enable runtime instrumentation. Both presets reuse the debug
Conan install — no extra `conan install` step is needed.

```bash
# AddressSanitizer + UBSan
cmake --preset sanitize
cmake --build --preset sanitize
ctest --preset sanitize

# ThreadSanitizer (incompatible with ASan — run separately)
cmake --preset tsan
cmake --build --preset tsan
ctest --preset tsan
```

`ORION_SANITIZE=ON` and `ORION_TSAN=ON` are CMake cache options set by their respective presets.
They can also be passed manually when using a custom configuration.

See [testing.md](testing.md) for guidance on interpreting TSan output and what to do when a
data race is found.

## Coverage

The `coverage` preset instruments the binary with LLVM source-based coverage. The test preset
sets `LLVM_PROFILE_FILE` so profile data lands in `build/Coverage/`.

```bash
cmake --preset coverage
cmake --build --preset coverage
ctest --preset coverage
cmake --build --preset coverage --target coverage-report
```

The `coverage-report` CMake target merges the raw profiles and prints a line-coverage summary to
stdout. CI enforces a minimum line coverage of 60% — raise the threshold in
`.github/workflows/ci.yml` as the test suite grows. See [testing.md](testing.md) for how to read
the report and what each coverage metric means.

## Fuzz targets

Fuzz targets live in `tests/fuzz/` and are only built when `ORION_FUZZING=ON` (set automatically
by the `fuzz` preset). They use libFuzzer as the entry point and run under ASan.

```bash
cmake --preset fuzz
cmake --build --preset fuzz

# Smoke run (verify no immediate crash)
./build/Fuzz/tests/fuzz/fuzz_topic -runs=10000 -max_len=4096 -timeout=10

# Extended campaign with corpus
mkdir -p corpus/fuzz_topic
./build/Fuzz/tests/fuzz/fuzz_topic corpus/fuzz_topic/ -max_len=4096
```

Add new fuzz targets to `tests/fuzz/CMakeLists.txt` following the pattern in
`tests/fuzz/fuzz_topic.cpp`. Each new target needs `-fsanitize=fuzzer` in its
`target_link_options`. See [testing.md](testing.md) for the full guide: when to add targets,
how to write them, how to interpret crashes, and how to manage a corpus.

## Cross-compilation (ARM64)

See [cross-compilation.md](cross-compilation.md) for the full workflow. The short version:

```bash
conan install . \
  --profile:build=conan/profiles/x86_64/debug \
  --profile:host=conan/profiles/arm64/debug \
  --output-folder=build/CrossArm64 \
  --lockfile=conan.lock

cmake --preset cross-arm64
cmake --build --preset cross-arm64
```

No `ctest` step — the resulting binaries target aarch64 and cannot run on x86. In CI, ARM64 is
tested natively instead; see [ci-cd.md](ci-cd.md).

## Generating documentation

**Docs: Generate (Doxygen)** runs the `docs` CMake target, which:

1. Creates `docs/_build/doxygen/` if it does not exist
2. Passes `ORION_PROJECT_VERSION=<version>` as an environment variable to Doxygen — the value
   was captured from `git describe --tags --abbrev=0` at CMake configure time
3. Runs `doxygen docs/Doxyfile`

The output HTML is written to `docs/_build/doxygen/` (gitignored). The version string is embedded
in the generated pages.

See [versioning.md](versioning.md) for how to tag a release so the correct version appears in the
documentation.
